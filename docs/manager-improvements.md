# 管理器 0.2.0

## 首次启动

EXE 优先查找所在目录的工作区，其次使用 Windows 用户注册表 `Software\FC27CareerLab\Manager` 中保存的工作区位置，最后询问连接已有目录或创建新工作区。`--workspace` 覆盖这些选择；`--smoke-test` 不写启动偏好。

新工作区在所选位置下创建 `FC27-workspace`，必须使用新目录或空目录，拒绝游戏安装目录及其子目录、目录链接和 EXE 解包目录。只复制自有研究方案和配置示例，创建 `local/inputs` 与忽略 local 的 `.gitignore`。Windows 启动偏好只保存路径；研究数据、任务日志、配置和备份仍在外部工作区 local。

进入“工作区设置”，使用向导填写只读游戏目录和 local 内的资产导出、参考包、静态 SDK、共享类型表与解压依赖。保存时在 `local/onboarding` 生成独立配置，保留旧配置与候选。Steam 检测只读取固定库路径和 `libraryfolders.vdf`，不扫描存档或账号目录。

依赖清单检查路径、普通文件、导出校验标记和已知解压库的散列；不会执行 SDK 或未知 DLL。输入缺失时仍可管理已有候选，但构建按钮与构建接口会拒绝继续。输入存在不等于内容完全适配，编译时仍会验证 GUID、签名、名称哈希、共享类型来源和游戏版本。

## 进度与恢复

流水线通知实际进入的阶段与研究资产读取数量；`pipeline-report.json` 增加 `stage_seconds`。没有预计百分比。任务历史保存在 `local/task-history/<管理目录标识>`，最近 50 项跨重启保留。重启后运行中的任务标为中断，不重放修改；历史成功预检不作为当前会话的已验证标签。

即使操作异常与快照刷新异常同时发生，也会释放忙碌状态；历史写入失败显示提示，不改变已经完成的文件事务。工作区设置列出未登记输出，保留失败报告与中间文件。重试构建使用新标识，不能覆盖原输出。副本恢复继续使用完整备份、事务绑定与当前文件校验，不增加自动覆盖或删除功能。

构建、合并与副本创建前要求工作区至少有 512 MiB 可用空间。这是最低空间门槛，不是整个构建峰值空间保证；实际写入失败仍保留输出供检查。

## 构建效率

单模块研究在解码参考资产前筛选，完整方案格式仍先校验。输出保留完整原始方案的散列与内容，报告明确 `selected_module`；未选模块的不兼容资产不会拖入该模块实验，但合并包仍审查全部选择。

静态类型缓存仅存活于单次操作，最多 4 项；键包含 SDK、共享类型、导出清单内容散列和完整 GUID 集。返回独立副本，防止调用者更改缓存。游戏源文件散列、共享类型来源、资产与 Bundle 引用检查仍每次执行，不缓存预检结论或已编译载荷。报告增加 `schema_cache` 命中计数，不承诺固定速度提升。

## 离线加载诊断

设置页面列出七项证据门槛。导出写到 `local/diagnostics`；内容省略本机路径、界面令牌、原始错误和游戏载荷。导出时读取候选的加载副本报告并核对登记绑定散列，汇总头部是否保留、载荷是否改变、签名区域状态与报告记载的挂载范围。这是绑定报告核对，不是再次重建挂载或引擎验证。

`loadable_mod`、加载兼容性与比赛效果保持 false。缺少前代原版基线继续标为 missing；实机读取证据与比赛对照标为 deferred。当前没有可靠依据解决签名接受性或实际 profile，不能用诊断界面把它们改成已支持。

## 自动发行

唯一版本来源为 `src/fc27_version.py`。构建器据此生成 Windows 文件版本、说明、ZIP 文件名和清单，并记录源提交与工作区是否有未提交更改。

`.github/workflows/windows.yml` 在 Windows 上运行无需真实游戏的测试并打包，上传 ZIP、SHA256 与清单。版本标签 `v<版本>` 必须与源码版本完全一致，通过后才发布 GitHub 预发行版。主分支及 PR 构建不发布版本；第三方 Actions 固定为核对过的提交 SHA。公开发行物不包含本机 local、游戏或研究资源。
